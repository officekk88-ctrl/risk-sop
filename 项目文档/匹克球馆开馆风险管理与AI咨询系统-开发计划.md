## 1. 计划目标

本计划用于指导匹克球馆开馆风险管理与 AI 咨询系统 Web 版 MVP 的产品设计、专业规则准备、软件开发、测试、试运行和上线工作。

MVP 上线后，应完成以下核心闭环：

```text
创建项目
  → 建立候选场地
  → 生成尽调清单
  → 上传并分析材料
  → 识别和登记风险
  → 创建整改任务
  → 发起人工复核
  → 完成阶段决策
  → 生成并归档报告
```

AI 能力应贯穿咨询、文件分析、风险建议和报告辅助生成，但重大风险、正式审核结论和阶段决策必须保留人工确认机制。

## 2. 计划假设

### 2.1 建议团队配置

| 角色 | 建议人数 | 主要职责 |
| --- | ---: | --- |
| 产品负责人/项目经理 | 1 | 范围、排期、需求、验收和跨团队协调 |
| 领域专家负责人 | 1 | 统筹法律、消防、工程、运营等专业规则 |
| 领域专家 | 2～4，兼职 | 规则、样本、提示词结果和报告审核 |
| UI/UX 设计师 | 1 | 信息架构、原型、设计规范和可用性测试 |
| 前端工程师 | 2 | Web 页面、交互、状态管理和实时对话 |
| 后端工程师 | 2 | 业务服务、权限、文件、工作流和报告 |
| AI 工程师 | 1～2 | 模型接入、检索、文档分析、评测和安全控制 |
| 测试工程师 | 1～2 | 测试设计、自动化、回归和验收支持 |
| DevOps/安全工程师 | 0.5～1 | 环境、发布、监控、备份和安全基线 |

若团队少于上述配置，应优先削减并行工作量或延长周期，不建议通过降低权限、安全、审计和测试要求压缩工期。

### 2.2 排期假设

- 采用两周一个 Sprint，共 10 个 Sprint；
- 第 1～4 周完成产品、专业规则和技术基础；
- 第 5～14 周完成核心业务闭环；
- 第 9～16 周并行建设 AI、知识库和报告能力；
- 第 17～18 周完成系统级测试和安全整改；
- 第 19～20 周进行真实项目试运行和生产发布；
- 产品、领域专家、研发和测试在整个周期持续参与；
- 首版面向一个试点城市或一组规则相近的地区；
- 首版主要适配桌面端，同时保证常用页面在移动浏览器中可查看和处理基础任务。

### 2.3 技术假设

- 前端采用 React、Next.js 和 TypeScript；
- 后端采用 NestJS 或 FastAPI，技术选型在 Sprint 1 锁定；
- 主数据库采用 PostgreSQL；
- 文件使用兼容 S3 的对象存储；
- 异步任务采用 Redis 和任务队列；
- AI 由服务端接入 OpenAI Responses API；
- 实时文本使用 Server-Sent Events，确有双向实时需求时再引入 WebSocket；
- 知识检索首选 PostgreSQL 全文检索与 pgvector，数据规模明显增长后再评估独立搜索服务；
- 所有外部服务通过适配层封装，避免业务代码绑定单一供应商。

## 3. 交付范围

### 3.1 P0：MVP 必须交付

1. 账号、机构、用户、角色和项目级权限；
2. 项目创建、项目状态和项目驾驶舱；
3. 候选场地建档及基础比较；
4. 开馆阶段流程、检查清单和决策门；
5. 文件上传、分类、预览、版本和证据关联；
6. AI 实时咨询及项目上下文加载；
7. PDF、Word、图片类材料解析与 AI 初审；
8. 基础合同、产权和证照审核规则；
9. 风险台账、风险等级和风险状态；
10. 整改任务、证明材料、复核和关闭；
11. 专家复核任务及意见提交；
12. 阶段审核、审批和决策结论；
13. 基础知识库、版本和发布状态；
14. 综合报告在线预览及 PDF 导出；
15. 站内消息及基础邮件提醒；
16. 系统配置、操作日志和 AI 调用日志；
17. 测试、监控、备份、安全基线和生产部署。

### 3.2 P1：时间允许时交付

- 候选场地可配置权重和高级评分；
- Word 报告导出；
- 企业级统计看板；
- 短信或企业协作平台通知；
- 更细粒度的字段权限和文件动态水印；
- 多种报告模板和报告版本对比；
- 专家资质到期提醒；
- 高级全文搜索和相似案例推荐。

### 3.3 P2：不纳入 MVP

- 专家交易、定价、支付和结算；
- 电子签章；
- 政府审批系统直接连接；
- 自动调取不动产或工商登记数据；
- BIM/CAD 深度识别；
- 原生移动 App；
- 多语言；
- 完整 ERP、财务记账和门店运营系统；
- 自动替代持证机构出具正式专业结论。

## 7. 任务依赖与关键路径

### 7.1 核心关键路径

```text
试点范围确认 EXP-01
  → 专业流程与规则 EXP-02/03/04
  → PRD 与状态机 PRD-02/04
  → 数据模型和架构 ARC-01/02
  → 项目、流程和清单 PJT/WFL/CHK
  → 文件、风险和任务 DOC/RSK/TSK
  → 决策门 DEC
  → AI 初审 AIP/AID
  → 报告 RPT
  → 系统测试 QA
  → 真实项目试运行 PILOT-01
  → 生产发布 REL-01
```

### 7.2 主要阻塞关系

- 未确定试点城市，不能冻结政策知识库和属地检查规则；
- 未取得合法脱敏样本，不能完成 AI 文件审核评测；
- 未完成角色权限矩阵，文件中心和专家协作不能进入稳定开发；
- 未完成风险和任务状态机，决策门和报告无法正确聚合；
- 未完成知识版本及引用定位，AI 回答不能满足证据可追溯要求；
- AI 评测不达标时，不允许自动生成可直接发布的审核结论；
- 安全高危问题未关闭时，不允许进入生产环境。

## 8. 详细迭代计划

### Sprint 1：启动、范围和技术预研（第 1～2 周）

#### 目标

建立团队协作机制，确认试点范围、MVP 边界、用户旅程和核心技术可行性。

#### 计划工作

- 完成 PM-01～PM-03；
- 完成 EXP-01，启动 EXP-02～EXP-06；
- 完成 PRD-01，启动 PRD-02～PRD-04；
- 完成 UX-01，输出核心低保真原型；
- 完成 ARC-01 技术选型；
- 验证文件上传、文档解析、流式 AI 输出和中文 PDF 生成；
- 建立仓库、代码规范和基础开发骨架；

## 10. 非功能要求与验收基线

以下指标为 MVP 建议基线，技术方案确认后应转化为可执行测试条件。

### 10.1 性能

- 普通业务页面在正常网络下首屏可用时间不超过 3 秒；
- 非 AI 核心 API 的 P95 响应时间不超过 800 毫秒，不包含文件上传和报告生成；
- AI 对话在模型服务正常时，首个流式内容目标不超过 5 秒；
- 100 页以内标准 PDF 的解析任务应在可接受时间内完成，并提供进度状态；
- 报告生成、文档解析等长任务必须异步执行，不阻塞 Web 请求；
- 首版容量测试基线：100 个并发在线用户、10 个并发 AI 请求，可根据真实规模调整。

### 10.2 可用性和可靠性

- 月度服务可用性目标不低于 99.5%，计划维护除外；
- 外部 AI、OCR 或邮件服务不可用时，核心项目管理功能仍可使用；
- 异步任务支持幂等、重试和死信处理；
- 关键业务写操作防止重复提交；
- 数据库和文件存储具备定期备份；
- 明确 RPO 和 RTO，MVP 建议 RPO 不超过 24 小时、RTO 不超过 4 小时。

### 10.3 安全

- 所有业务请求经过身份认证和权限校验；
- 机构、项目、文件和专家资料严格隔离；
- API 密钥及数据库凭据不进入前端和代码仓库；
- 文件上传进行类型、大小和恶意内容检查；
- 敏感操作记录不可由普通管理员篡改；
- 防范常见 Web 漏洞、越权访问和提示注入；
- 发布前完成依赖漏洞扫描和权限专项测试；
- 严重和高危安全问题必须在上线前关闭。

### 10.4 可维护性

- 核心业务采用清晰的领域边界；
- 数据库变更全部通过迁移脚本管理；
- API 具备版本策略和机器可读规范；
- 流程、清单、风险规则、提示词和报告模板支持版本化；
- 关键逻辑必须有自动化测试；
- 日志使用统一追踪 ID；
- 外部服务通过适配层接入。

### 10.5 可访问性和兼容性

- 支持最近两个稳定版本的 Chrome 和 Edge；
- 支持常见桌面分辨率；
- 核心查看、待办和审批页面适配移动浏览器；
- 风险状态不能仅依赖颜色表达；
- 表单具有明确标签、错误提示和键盘操作能力。

## 11. AI 质量计划

### 11.1 评测集组成

首版应准备经过脱敏和合法授权的评测数据：

- 租赁合同样本；
- 不动产权证或同类权属材料样本；
- 主体资格和授权文件样本；
- 消防、规划和工程证照样本；
- 存在缺页、模糊或签章异常的样本；
- 主体、地址、用途、期限和金额存在矛盾的多文件组合；
- 常见咨询问题和标准专业答案；
- 应明确拒绝确定结论并转人工复核的案例；
- 提示注入和越权获取资料的对抗样本。

### 11.2 评测指标

| 指标 | 说明 | MVP 建议门槛 |
| --- | --- | --- |
| 文件分类准确率 | 文件类型识别正确比例 | ≥ 95% |
| 关键字段准确率 | 主体、地址、期限等字段准确比例 | 核心字段 ≥ 95% |
| 重大风险召回率 | 标准答案中的重大风险被识别比例 | ≥ 90% |
| 引用正确率 | 引用确实支持对应结论的比例 | ≥ 95% |
| 无依据确定结论率 | 无依据却输出确定判断的比例 | ≤ 2% |
| 人工复核路由准确率 | 应转专家的场景被正确识别 | ≥ 95% |
| 结构化输出成功率 | 输出可被系统正确解析 | ≥ 99% |

上述指标需要按文件类型分别统计，不能仅使用总体平均值掩盖单类文件问题。

### 11.3 AI 发布门槛

- 评测集和标准答案经过领域专家确认；
- AI 回答明确区分事实、推断、建议和待核实事项；
- 重大风险漏检案例完成根因分析；
- 所有引用可定位到项目文件或知识来源；
- AI 不能绕过用户权限读取资料；
- AI 不能自行批准阶段或关闭风险；
- 模型、提示词、规则和知识版本可追溯；
- 模型升级必须重新运行基准评测和回归测试。

## 12. 测试计划

### 12.1 测试层级

- 单元测试：状态机、评分、权限、规则和数据转换；
- 组件测试：表单、文件、表格、审批和对话组件；
- API 集成测试：认证、项目、文件、风险、任务和报告接口；
- 端到端测试：从创建项目到生成报告的核心流程；
- AI 评测：字段、风险、引用、拒答和专家路由；
- 安全测试：越权、上传、注入、依赖和敏感数据；
- 性能测试：API、上传、队列、AI 并发和报告生成；
- 恢复测试：数据库、文件、任务队列和版本回滚；
- 用户验收测试：真实角色和真实项目场景。

### 12.2 核心端到端用例

1. 管理员创建机构并邀请项目负责人；
2. 项目负责人创建项目和多个候选场地；

4. 项目成员上传产权、合同和证照材料；
5. AI 解析文件并提出缺失项和风险；
6. 审核人员确认、修改或驳回 AI 建议；
7. 重大风险生成整改任务并阻断决策门；
8. 项目负责人补充材料并提交复核；
9. 专家完成专业复核并提交意见；
10. 审核人员关闭风险或保留附加条件；
11. 决策人批准有条件通过；
12. 系统生成并导出综合报告；
13. 所有关键操作在审计日志中可追溯。

### 12.3 缺陷发布标准

- 阻断级缺陷：0；

## 15. 主要项目风险与应对

| 风险 | 影响 | 预警信号 | 应对措施 |
| --- | --- | --- | --- |
| 试点范围长期不确定 | 政策、规则和知识库无法冻结 | 多城市需求反复变化 | 先锁定一个城市，其他地区进入后续版本 |
| 领域专家投入不足 | 规则和 AI 标准答案质量不足 | 评审延期、意见冲突 | 提前锁定专家时间，明确最终专业负责人 |
| 缺少合法真实样本 | 文档审核无法可靠评测 | 只能使用简单模拟文档 | 提前收集、授权、脱敏并标注样本 |
| MVP 范围膨胀 | 核心闭环延期 | Sprint 持续加入 P1/P2 | 执行变更评审，功能冻结后进入版本池 |
| AI 结论不稳定 | 误导用户或漏检风险 | 相同材料结果差异大 | 结构化输出、规则兜底、评测和人工确认 |
| 政策知识过期 | 引用失效或地区错配 | 无复核日期、来源不明 | 版本、地区、有效期和定期复核机制 |
| 多租户越权 | 严重数据泄露 | 权限逻辑分散、测试不足 | 服务端统一鉴权、数据隔离和越权专项测试 |
| 大文件解析成本高 | 响应慢、成本失控 | 队列积压、AI 用量异常 | 限制大小、分段处理、缓存和配额告警 |
| 外部服务不可用 | AI、OCR 或通知中断 | 错误率持续升高 | 超时重试、熔断、降级和人工处理路径 |
| 报告被误认为正式鉴定 | 法律和声誉风险 | 用户忽视 AI 边界 | 页面提示、报告声明、流程阻断和专家复核 |
| 数据保留规则不清 | 隐私和合规风险 | 文件无法彻底删除 | 数据分类、保留期限、删除流程和审计 |
| 上线后缺乏运营维护 | 内容过期、问题无人处理 | 知识长期不更新 | 明确内容、产品、技术和客服责任人 |

## 16. 项目管理机制

### 16.1 固定会议

| 会议 | 频率 | 参与人 | 输出 |
| --- | --- | --- | --- |
| 每日站会 | 工作日每日 | 研发、测试、产品 | 进度、当天计划、阻塞事项 |
| 产品与专家评审 | 每周 | 产品、领域专家、研发代表 | 规则、原型和专业结论 |
| Sprint 计划会 | 每两周 | 全体核心成员 | Sprint 目标和承诺范围 |
| Sprint 评审会 | 每两周 | 团队和业务负责人 | 可运行成果和验收意见 |
| Sprint 复盘会 | 每两周 | 项目团队 | 改进事项和责任人 |
| 项目风险会 | 每周 | 项目经理和负责人 | 风险变化、决策和升级事项 |

### 16.2 需求变更规则

- 所有新增需求先判断属于 P0、P1 还是 P2；
- 进入 Sprint 后原则上不增加范围，除非属于阻断或重大风险；
- P0 变更必须说明业务价值、影响范围、追加成本和排期变化；
- 需求变更必须同步更新 PRD、原型、测试和发布说明；
- 功能冻结后，非上线阻断项进入 V1.1 待办池。

### 16.3 进度报告

每周进度报告至少包含：

- 里程碑状态；
- 本周完成事项；
- 下周计划；
- 阻塞事项；
- 范围变化；
- 质量数据；
- 项目风险；
- 需要决策的问题。

## 17. Definition of Ready

研发任务进入 Sprint 前应满足：

- 用户价值和使用角色明确；
- 业务规则和范围明确；
- 页面原型或接口说明具备；
- 权限、状态和异常场景明确；
- 验收标准可测试；
- 依赖项已完成或有明确计划；
- 所需专业内容或样本已经提供；
- 不存在影响实现方向的未决问题。

## 18. Definition of Done

研发任务标记完成前应满足：

- 功能代码完成并通过代码评审；
- 单元和必要的集成测试完成；
- 权限和异常场景验证通过；
- 日志、监控和审计按要求接入；
- 数据库变更包含迁移和回滚说明；
- API 和用户文档已更新；
- 测试环境验证通过；
- 无阻断或严重缺陷；
- 产品负责人验收；
- 涉及专业规则或 AI 输出的功能经领域专家抽检；
- 变更已包含在版本发布说明中。

## 19. MVP 总体验收标准

### 19.1 业务验收

- 可以创建机构、用户、项目和候选场地；
- 可以根据场地信息生成适用流程和尽调清单；
- 可以上传、分类、预览、更新和关联项目材料；
- 可以创建风险、整改任务并完成复核关闭；
- 重大风险可以阻断阶段决策；
- 可以发起专家复核并接收专业意见；
- 可以生成、审核、批准和导出综合报告；
- 一个真实项目可以完整走通核心闭环。

### 19.2 AI 验收

- 支持项目内实时流式咨询；
- 回答能引用授权项目材料和已发布知识；
- 文件初审能够输出结构化字段、问题、风险和缺失项；
- AI 结论和人工确认结论分开存储；
- 用户确认后才能将 AI 建议写入正式风险和任务；
- 高风险、低置信度和资质事项能够路由人工复核；
- 基准评测达到约定门槛；
- AI 故障时不影响非 AI 核心业务。

### 19.3 技术和安全验收

- 多机构、多项目数据隔离通过专项测试；
- 核心操作和 AI 调用可审计；
- API 密钥和敏感凭据未暴露；
- 文件、数据库、备份和传输满足安全基线；
- 性能、兼容性和恢复测试通过；
- 无未关闭的阻断、严重缺陷和高危安全问题；
- 生产监控、告警、备份和回滚机制可用。

## 20. 开发前必须确认的决策

以下事项应在 Sprint 1 结束前确认，否则可能影响范围和排期：

1. 首个试点城市及行政区；
2. MVP 是企业内部系统还是对外 SaaS；
3. 第一批实际用户和项目数量；
4. 首批支持的材料类型；
5. 是否已有 SOP、合同模板、历史案例和脱敏样本；
6. 法律、消防、工程和运营专业负责人的人选；
7. 是否在 MVP 中提供真实的外部专家协作；
8. 数据部署位置和安全等级；
9. 预期并发、文件规模和 AI 使用预算；
10. 短信、邮件、电子签章等第三方服务范围；
11. 产品名称、品牌视觉和域名；
12. 上线审批人和最终验收人。

## 21. 后续文档清单

开发过程中还应逐步形成以下配套文档：

- 产品需求文档 PRD；
- 用户旅程和页面原型；
- 角色权限矩阵；
- 业务状态机说明；
- 系统架构设计；
- 数据库 ER 图和数据字典；
- API 规范；
- 文件分类和字段字典；

- AI 架构、提示词和工具调用规范；
- AI 评测集及评测报告；
- 测试计划和测试报告；
- 安全设计和安全测试报告；
- 部署、备份、恢复和回滚手册；
- 用户、管理员和知识维护手册；
- 试运行报告和上线复盘报告。

## 22. 结论

本计划以 20 周为 Web 版 MVP 基线，通过双周迭代逐步完成专业规则、基础平台、核心业务、AI 文件审核、专家复核、报告和上线保障。

项目执行时应始终优先保证以下四项能力：

1. 项目业务流程能够完整走通；
2. 风险、整改和决策过程能够形成闭环；
3. AI 结论具有依据、边界和人工复核机制；
4. 敏感材料、权限和关键操作安全可追溯。

在上述能力稳定之前，不应通过增加后续扩展功能牺牲 MVP 的专业质量、数据安全和上线可靠性。
